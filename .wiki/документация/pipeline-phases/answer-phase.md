# Фаза ANSWER

Финальная фаза SQL-пайплайна агента, формирующая ответ пользователю на основе результатов выполнения (SQL, файловые чтения, поиск). Синтезирует JSON-ответ с обоснованием, текстом сообщения и ссылками на позиции каталога.

## Основные характеристики

- Выходной формат: чистый JSON (первый символ обязательно `{`)
- Поле `reasoning` — трассировка цепочки: сырой результат → интерпретация → вывод; обязательны конкретные таблицы/колонки/пути
- Поле `message` — текст ответа пользователю; для вопросов да/нет обязателен тег `<YES>`/`<NO>`; для COUNT-задач — обязателен токен `<COUNT:n>` и ≥1 ключевого слова категории
- Поле `outcome` — статус завершения задачи (см. таблицу ниже)
- Поле `grounding_refs` — пути к каждой совпавшей записи; источник зависит от типа execute
- Поле `completed_steps` — краткий список выполненных шагов (2–5 элементов)

## Типы outcome

| Значение | Когда использовать |
|----------|-------------------|
| `OUTCOME_OK` | Задача выполнена успешно с доказательствами. Если задача утверждает существование записей, а `grounding_refs` пустой — это НЕ OUTCOME_OK |
| `OUTCOME_NONE_CLARIFICATION` | Текст задачи действительно неоднозначен и SQL не может его разрешить; ИЛИ утверждённые существующие записи не найдены |
| `OUTCOME_NONE_UNSUPPORTED` | Тип запроса не поддерживается базой данных |
| `OUTCOME_DENIED_SECURITY` | Зафиксировано нарушение безопасности |

## Правила grounding_refs

Источник зависит от типа execute-результата:

| Тип результата | Источник grounding_refs |
|----------------|------------------------|
| SQL result | AUTO_REFS пути (точно как показано) |
| search: result (формат `path:line:line_text`) | поле `path` из каждой строки |
| list: result (только имена файлов) | имя файла + директория → абсолютный путь |
| read: result | путь к прочитанному файлу |

Запрещено конструировать пути вручную из сырых значений колонок при наличии AUTO_REFS.

## Требования к reasoning

`reasoning` ОБЯЗАН трассировать: сырой результат → интерпретация → вывод.

Обязательные шаги:
1. Сырой результат (буквальное значение, количество строк, совпавшие пути)
2. Интерпретация (что результат означает в контексте задачи)
3. Вывод (как результат отвечает на вопрос)

Для search-результатов: цитировать совпавшие пути и текст строки. Для SQL: называть таблицу, колонку, ключ фильтра и значение.

## Ограничения OUTCOME_NONE_CLARIFICATION

`OUTCOME_NONE_CLARIFICATION` допустим **только** если текст задачи объективно неоднозначен и SQL не может его разрешить. Наличие SQL-результатов (включая discovery-only: список моделей, список ключей) → обязательно `OUTCOME_OK`. Пустой `grounding_refs` при `OUTCOME_NONE_CLARIFICATION` — баг, не допустимое состояние.

Исключение: если задача утверждает, что записи существуют ("confirmed hit", "known fraud", "cite every X"), а `grounding_refs` пуст — использовать `OUTCOME_NONE_CLARIFICATION`.

## Clarification Guard (дополнительное правило)

Пустой SQL-результат из-за schema-mismatch (неизвестная колонка, неверное имя таблицы, отсутствующий ключ) — **не** является неоднозначностью задачи. Для общих lookup-задач использовать `OUTCOME_OK` с сообщением о том, что было найдено.
