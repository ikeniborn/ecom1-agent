1. Резюме спецификации

Офлайн-инструмент: из часто срабатывающей lint-проверки data/harness/checks.yaml дистиллируется положительный method-атом oracle, валидируется полным сквозным прогоном задачи-источника и промотируется (candidate→active) только при оценке грейдера 1.0.

СекцияТребование
ScopeОфлайн-инструмент per hot-check: distil → validate → promote; переиспользует существующую машинерию distil/validate/promote.
DecisionsРазмещение — офлайн-скрипт (нулевая runtime-стоимость).
DecisionsГейт валидации — efficacy через полный pipeline (INTENT → INVESTIGATE → PLAN-loop) с инжектированным атомом.
Architecture §1Оркестратор scripts/harness_to_oracle.py (new): aggregate → load_checks → отбор hot-checks → per-check distil/validate/promote → сводка.
Architecture §2Efficacy-валидатор agent/oracle_validate.py (extend): grade_full_run + validate_atom_via_full_run; ленивый импорт run_agent против цикла импорта.
Architecture §3Сем инъекции agent/oracle.py (extend): _active() учитывает ECOM_ORACLE_FORCE_ACTIVE, делая один candidate-атом видимым для retrieve на время одного прогона.

TestingЮнит-тесты для _active, validate_atom_via_full_run, оркестратора (через monkeypatch).

Success Criteria (критерии приёмки, из тела спеки)

#Критерий
SC-1Промоут атома происходит только при сквозной оценке грейдера 1.0 (efficacy-гейт).
SC-2Идемпотентность: повторный запуск скрипта не раздувает oracle — dedup по косинусу (ECOM_ORACLE_DEDUP_COSINE), без always-on ledger.
SC-3Нулевая runtime-стоимость: вся логика офлайн, грейдер-round-trips вне основного прогона.
SC-4Без мутации data/oracle/atoms.yaml до промоута; ECOM_ORACLE_FORCE_ACTIVE чистится в finally (не утекает в последующие прогоны).
SC-5Изоляция: при unset env поведение идентично текущему (back-compatible).
