Корневой баг (run 3) — контракты примитивов

SQL отработал правильно, строка вернулась. Упал compute-шаг интерпретатора:

Трасса краша: first → column

PLAN.compute:

{"prim": "first",  "args": ["$row"],                 "into": "first_row"}
{"prim": "column", "args": ["$first_row","product_name"], "into": "product_name"}
  • first($row) → $row = rowset (list[dict]) → вернул один dict.
  • column($first_row, …) — операция над списком (primitives.py:26): 
    def _column(rows, col):
    return [r.get(col) for r in (rows or [])]
  • Итерация по dict даёт его ключи-строки. Значит r = "product_sku" → "product_sku".get(col) → 'str' object has no attribute 'get'. 💥
  • Для одиночного dict нужен примитив get (есть, primitives.py:47), а не column. Модель перепутала контракты.
Почему 1 цикл вместо retry

Краш классифицируется как real_vm-исключение. _is_retryable_vm_error (pipeline.py:73) проверяет строку по _RETRYABLE_VM_ERROR_PATTERNS. 'str' object has no attribute 'get' туда не входит → не retryable → break → терминальный CLARIFY за 1 цикл.

Что выучил iLEARN (мимо цели) 
rule: "Always use an explicit rowset format (e.g. 'csv'/'json')…
       include a validation step to ensure rowset contains dicts…"

iLEARN обвинил format / PLAN за баг примитива интерпретатора. LEARN не правит код → правило бесполезно и засоряет store. На t01 уже 6 learned-правил — всё равно фейл.

Системные проблемы агента

#ПроблемаЗвеноСерьёзностьЭффект
1 Untyped Plan-IR + lint не типизирует. Модель пишет тип-некорректную композицию (list-op на скаляр) → краш Python в interpret. lint / interpret Критич. Класс багов; корень провала t01 run 3
2 iLEARN лечит баг кода как знание задачи. Пишет правила про format/SQL для дефекта интерпретатора. iLEARN Критич. Засорение store; обучение не сходится
3 verify не блокирует битый OK. OK-ответ эмитнут при нерезолвнутом required ref. verify Высок. run 1: «missing required reference»
4 answer-once необратим. Плохой ответ приземлился → recovery невозможен (answer already provided). answer/loop Высок. run 1 цикл 2 потрачен впустую
5 Хрупкий exact-match vs re-seed. INTENT.success_criteria зашивает значения (eq model='…'), данные пере-сидируются на каждом StartRun. INTENT Средн. run 2: false UNSUPPORTED
6 Exec//bin/sql stdin недетерминирован. Иногда возвращает man-page вместо данных. interpret / VM Средн. run 1: пустой rowset, тихо
7 DOC_SELECT мимо. Выбрал checkout/returns/warehouse/store-associate для чисто каталожного запроса. DOC_SELECT Низк. Здесь безвредно; точность отбора низкая
