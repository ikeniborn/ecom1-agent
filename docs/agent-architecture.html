Архитектура агента ecom1

Plan-IR интерпретатор · ветка heuristics · обновлено 2026-06-18 · источники: CLAUDE.md, agent/CLAUDE.md, agent/*.py, docs/wiki/

Детерминированный Plan-IR интерпретатор. Одна задача — один проход: INTENT → loop[PLAN → auto-repair → lint → interpret → verify] → answer-once. Единственный quality-gate — детерминированный verify(). Агент не грузит все данные заранее: INTENT получает полный контекст один раз, PLAN — тонкий, а тяжёлые данные добираются по запросу через IR discovery-шаги. Знания копятся в двух контурах: правила задачи (data/learned) и общие знания оракула (data/oracle) с полярностью «метод / анти-паттерн» на успехах и провалах.

Ключевой инвариант: vm.answer(...) вызывается ровно один раз за задачу — успешный путь или один терминальный OUTCOME_NONE_CLARIFICATION.

1. Контейнеры и компоненты

2. Обработка доступной информации и инструментов

orchestrator.py:run_agent() до пайплайна открывает VM, читает /AGENTS.MD напрямую и собирает facts. Из /AGENTS.MD детерминированно (0 LLM) строится инвентарь инструментов и каталогов (render_inventory): tools/rpcs: — доступные RPC/инструменты, catalog/paths: — каталожные/файловые пути. Это компактная замена многословного документа.

Tiering фактов — кто что видит

Раньше _facts_block инжектил все факты в INTENT и в каждый PLAN-цикл (27–29 K символов, пересылаемых заново → context drift). Теперь факты режутся по фазам: INTENT (один frozen-вызов) получает полный набор; PLAN (повторяется) — тонкий, тяжёлые данные добираются по запросу.

_facts_block(facts, tier): run_intent → tier="intent", run_plan → tier="plan". Красные блоки выброшены из upfront-инъекции PLAN и добираются через discovery. При LOG_LEVEL=DEBUG run_plan печатает размер PLAN-промпта.

Цель: PLAN-промпт для t01 падает с ~28 K до < ~10 K символов — главный рычаг против context drift.

3. Поток выполнения задачи

Фазы подробно
  • INTENT (reason.py:run_intent, reason-tier, 1 вызов, frozen, retry на пустой/parse-fail по DESIGN_MAX_ATTEMPTS) → IntentSpec: objective, desired_outcome, params, outcome_space, constraints, success_criteria (keyed by outcome), answer_shape, required_refs. Hard-fail → terminal CLARIFICATION.
  • PLAN (reason.py:run_plan, reason-tier) вход: [intent, thin-facts, learn_ctx, prev_error?, oracle_atoms, observed?] → PlanIR: discovery, rowsets, compute, decision, ops, answer, custom_extract.
  • auto-repair (_repair_plan_dict) — детерминированно, без LLM, до PlanIR(**obj): маппит op-синонимы (neq→ne, !=→ne, ==→eq, gte→ge, lte→le) и срезает лишние ключи answer-веток. Немаппируемое падает на валидации → PlanError → iLEARN.
  • lint (interpreter.lint_security_first) — без LLM. PlanError/InterpretError → _ilearn.
  • plan-signature — _plan_signature(plan) по discovery+ops (SQL нормализован, прочие args verbatim). Anti-infinite-loop guard.
  • interpret (interpreter.interpret) — без LLM; discovery-шаги добирают данные по запросу. InterpretError → retry; реальная VM-ошибка → retry только если plan read-only И ошибка retryable (_is_retryable_vm_error), иначе break.
  • verify (verify.verify) — детерминированный, без LLM. Применяет критерии только выбранного outcome. Единственный gate перед answer.

4. Исходы цикла

5. Получение данных по запросу (probe-then-refine)

Тяжёлые данные (sample-строки, тела записей, тексты политик) не инжектятся в PLAN заранее — PLAN добирает их сам через discovery-шаги. Механизм переиспользует существующий цикл: вывод RPC возвращается в следующий PLAN-вызов через аргумент observed. Новой фазы нет.

6. Накопление знаний — два контура

Агент учится в двух независимых контурах: один привязан к задаче (правила, как решать именно её), второй — общий межзадачный (методы и анти-паттерны, переносимые между задачами).

Контур задачи · data/learned/{tid}.yaml

  • Где: внутри прохода (между циклами) + в training-режиме между прогонами.
  • Триггер: провал цикла / grader-feedback → _ilearn → LearnConsolidate diff.
  • Область: только эта задача; PLAN видит все active-правила задачи.
  • Полярность: корректирующее правило формы PLAN.

Контур общих знаний · data/oracle/atoms.yaml

  • Где: межзадачно; ретривится семантически в PLAN любой подходящей задачи.
  • Триггер: grader-score в конце прогона → distill_from_grader.
  • Область: generic-методы, переносимые; засеян стартовый набор.
  • Полярность: method · APPLY на успехе, anti_pattern · AVOID на провале.

Self-fill оракула по grader-score

distill_from_grader(task_id, score, score_detail) заполняет банк из счёта, который уже вернул SubmitRun — без живого grader-round-trip. Успех (score ≥ 1.0) → атом-метод; провал → атом-анти-паттерн. Оба пишутся со status="active"; читают персистнутые IntentSpec+PlanIR; no-op без артефактов; никогда не бросают. main.py зовёт для каждой задачи (и успех, и провал).

Стоимость: self-fill — это один reason-tier distill-вызов на задачу, гейт только ORACLE_ENABLED (default on). N задач → +N вызовов сверх per-task бюджета. ORACLE_VALIDATE_INLINE=0 остаётся default — без живого grader во время обычного прогона.

7. LEARN-seam и персистентность (контур задачи)

_ilearn(...) оборачивает _learn_consolidate_text(...) (driven by rendered IntentSpec + PlanIR). Пишет diff в data/learned/{tid}.yaml, мутирует in-session learn_ctx, сохраняет prephase_deep_read хинты. Один surface — PLAN видит все active-правила.

learned_store.py: load_entries(tid) (только active), apply_learn_diff, save_last_run. _persist_artifacts пишет {tid}.intent.json + {tid}.plan.json — потребляются learn_from_grader (training) и distill_from_grader (self-fill).

Training mode (TRAIN_MAX_CYCLES > 1)

main.py оборачивает StartRun/SubmitRun во внешний loop. После SubmitRun задачи со score < 1.0 получают LEARN-правило из grader-feedback (без перезапуска INTENT/PLAN — читает персистнутые IntentSpec+PlanIR). Следующий cycle: свежий StartRun только по падающим задачам. Трейсы: {tid}.c{N}.jsonl.

8. Knowledge-oracle (контур общих знаний)

Семантический retrieval атомов знаний в PLAN (agent/oracle.py), master-toggle ORACLE_ENABLED. Банк засеян generic-методами (probe-then-refine, нормализация free-text, чтение управляющей /docs-политики).

При недоступном embedding-endpoint _cosine_topn падает, и _tag_fallback добирает по ключевым словам — retrieval всё равно возвращает атомы. build_oracle_block рендерит методы под «APPLY (verified methods)», анти-паттерны — под «AVOID (known failure causes)».

Две оси. Провайдер-транспорт по префиксу MODEL; per-phase модель по _resolve_model_for_phase.

Порядок: MODEL_<PHASE> → tier-env → MODEL. С одним MODEL всё резолвится в MODEL (back-compat). Transient (503/rate-limit/timeout) → exp-backoff → следующий tier → MODEL_FALLBACK.

LLM-бюджет (на задачу): 1 (INTENT hard-stop) / 2 (best: INTENT + 1 PLAN) / 1 + 2·INTERPRETER_MAX_STEPS (worst: каждый failing cycle = PLAN + iLEARN). Плюс +1 distill self-fill в конце прогона при ORACLE_ENABLED=1.

13. Значимые инварианты

  • One pipeline — только детерминированный Plan-IR интерпретатор; нет DESIGN/CODEGEN/TEST-GEN.
  • answer ×1 — ровно один вызов vm.answer за задачу.
  • verify() — единственный pre-answer gate, детерминированный; применяет критерии только выбранного outcome (валидный негатив проходит).
  • INTENT frozen — полный контекст один раз; обновления learn_ctx влияют только на последующие PLAN-циклы.
  • Тонкий PLAN + on-demand — тяжёлые факты не инжектятся заранее, добираются через discovery.
  • auto-repair fail-closed — мапит известные op-синонимы; немаппируемое всё равно падает на валидации (нет тихого приёма невалидного IR).
  • Два контура знаний — задача (data/learned) и общие методы/анти-паттерны (data/oracle) независимы.
  • plan-signature — anti-infinite-loop guard (заменил legacy SQL-multiset retry).
  • Prompt rules — task-specific знания только через LEARN/oracle; data/prompts/ не патчат под отдельную задачу (допустимы лишь generic-структурные правила).
  • Re-seed safety — правила/атомы остаются методами, не хардкод-значениями (бенчмарк ре-рандомит данные каждый StartRun).
