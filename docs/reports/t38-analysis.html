Главный вывод. Задача провалена механически, а не по логике: фаза PLAN дважды вернула пустой ответ (PLAN LLM returned empty response), по ~732 с каждый. План так и не построен → нет interpret/verify → vm.answer не вызван → терминальный OUTCOME_NONE_CLARIFICATION. 76% времени прогона ушло в два пустых вызова PLAN. 3. Корневая причина — механика

Обе попытки PLAN (цикл 1 и 2) завершились идентично: пустой ответ, 0 токенов, ~732 с, success=False. Так как PlanIR не построен, интерпретатор не запускался ни разу. Цикл-loop исчерпал 2 итерации → терминальный CLARIFICATION.

Три механических дефекта складываются в провал:
  • Пустой ответ CC-tier на самой большой фазе (system-prompt PLAN + intent + brief + 4 learned-правила + oracle). Вероятно — переполнение контекста/таймаут CC-subprocess при генерации крупного PlanIR JSON.
  • Нет fallback. ECOM_MODEL_FALLBACK не сработал — обе попытки тот же claude-code/sonnet. Пустой ответ не трактуется как исчерпание тира.
  • Таймаут не соблюдён. 732 с на вызов против ECOM_LLM_HTTP_READ_TIMEOUT_S=180 — CC CLI subprocess не подчиняется HTTP-таймауту.

4. Эффективность инструментов и пайплайна

INVESTIGATE — дорогой и не сошёлся

20 LLM-вызовов (router + digest + эскалации) при бюджете ECOM_INVESTIGATE_MAX_STEPS=6. Записи найдены, но sufficiency не достигнут: governing policy-doc остался непрочитан на момент исчерпания бюджета.

Стоимость этапа: router+digest ≈ 2–3 LLM-вызова на шаг + 4 отдельных RERANK (oracle-retrieve). При этом ключевое чтение doc не выполнено — бюджет потрачен на перечисление/группировку записей.

Сломанный учёт токенов на CC-tier

В каждом из 27 LLM-событий tokens_in=3424 — константа. Это не реальные per-call значения; итог in=3424/out=9802 совпадает лишь с числами INTENT. Per-phase стоимость по логу измерить невозможно — CC-subprocess не отдаёт usage надёжно.

Дыра логирования parsed_output

INTENT: success=True, tokens_out=9802, raw_response — валидный полный JSON (2030 байт), но parsed_output=null в логе. Фаза отработала (INVESTIGATE дальше использовал required_refs), значит null — дефект сериализации лога, а не сбой фазы. Усложняет автоматический разбор JSONL.

5. Семантика решения — куда шёл investigator

Логика разведки до обрыва была разумной: identity-gate (/bin/id → emp_011), нашёл payment_transactions, установил отсутствие dedicated fraud-таблицы, выделил 40 «застрявших 3DS» записей.

Но выбор 40 записей — по 3DS-прокси, не по Risk-Ops-confirmed сигналу. Записи отобраны по customer_abandoned / challenge_timeout (технические 3DS-исходы), тогда как задача требует записи подтверждённого Risk-Ops fraud-hit. Это ровно анти-паттерн, против которого направлено активное правило r015 («не подменяй authority-confirmed сигнал статистическим/структурным прокси») — и причина, по которой policy_doc_read=false критичен: governing doc определяет настоящий confirmed-сигнал.

Следствие: механический фейл PLAN замаскировал вероятный семантический фейл. Даже при рабочем PLAN ответ, построенный на 3DS-прокси, рисковал не пройти grader (over-/under-select относительно authority-confirmed набора). Поэтому фикс PLAN — необходимое, но недостаточное условие для score 1.0 на t38.

Поправка после чтения исходника. Настоящий код-баг — один: cfg={} на всех call-site → models.json cc_options мёртв. M1/M2 — не баги. Авторитетный источник — спек docs/superpowers/specs/2026-06-21-t38-pipeline-fixes-design.md.

Приоритет фиксов (после поправки)

  1. A1 + C2 (разблокировать PLAN). A1 — резолвить per-model cfg из models.json (код); C2 — задать ECOM_MODEL_FALLBACK (конфиг, fallback уже в коде). Снимает 76% потерянного времени и сам провал прогона.
  2. H2 + H3 (корректность answer). Детерминированно грунтовать governing-doc и резолвить confirmed-сигнал — необходимо для реального score 1.0, иначе PLAN строит план на прокси.
  3. M3 (стоимость INVESTIGATE). Слить digest(N)+router(N+1) в один вызов — срезает round-trip’ы. Средний риск.
  4. M1–M2 (опционально). Не баги; косметика наблюдаемости, делать только если дёшево.
